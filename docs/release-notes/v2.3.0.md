# Release notes — meta-pass v2.3.0

**In one line:** the three things users used to bet on every day — *will it fit, did it install, am I still connected* — are now protocol-level certainties: install success travels in the finalize response body with idempotent device retries, store sizes show the true storage footprint (app + DATA reservations), and the token renews on activity while dead on-screen codes heal themselves. Every fix was located through a real-device incident: truncated images, slot loss, false-negative install failures, dead codes.

## Fixes (real-device driven)

- **Extension-less ESP images parsed into truncated garbage (severe)**: the firmware parser probed "is there a 16-byte extension header after the 24-byte header" by walking whichever segment chain parsed — the wrong layout often "walked through" and produced an absurd length (real device: Pocket Radar unpacked to **176B**, truth 2,321,984B). The truncated image's SHA matched the page-side value (hashes only the prefix), every gate passed, and `esp_ota_end` finally blew up with `finalize verify failed`; each failure rolled back the carve, and after 4 retries **all slots were gone**. Now authoritative: for `hash_appended=1` (modern IDF default), SHA-256 over both layout candidates is compared against the image trailer; match wins, no match rejects. Cross-checked three ways with `esptool image_info`.
- **Store decision-page race (severe)**: between `offer_ready` and `confirmed`, prepare spends hundreds of ms on DATA migration + carve commit + partition-table rewrite + otadata erase; the 250 ms UI poll could push the stale decision page with no exit, and keypresses acted on a superseded offer (real incident: device stuck on an expired CONFIRM/BACK screen mid-install, all slots lost by the end). Both pages now have race exits.
- **Install succeeded but phone reported failure (false negative)**: after finalize the device left the store immediately → controlled reboot + token invalidation; the phone's done-poll fired into the void. The finalize 200 body now carries `{"state":"done","slot":N}` — success confirmed in a single request-response round trip, no timing bets.
- **Lost finalize responses**: phone retries up to 3 times with 3 s backoff; the device answers a retried finalize for a completed session with the same done JSON (idempotency anchor), so "committed but response lost" is never misjudged as failure. Three unanswered attempts report "state uncertain" and point the user at the device.
- **Fixed 30-min token expiry = death**: replaced by a sliding TTL (every authenticated request extends it) + P-256 phone hardware binding; on expiry the screen auto-reissues a pair code and the page guides re-pairing in place. 401s now carry machine-readable reasons (expired vs credential failures get distinct guidance) instead of everything reading "session expired".
- **Dead on-screen codes on the QR page (fixed on release eve)**: the page was a build-time snapshot; after the token's 30-min or the code's 5-min TTL the screen showed dead codes forever, recovery only via a 401 poke. store_tick now self-heals: expired token → full reissue; merely stale code → code-only reissue (slow-connecting phones not stranded); max-tries-dead codes recover too.
- **Bootloader booted via a stale mapping after carve table rewrite**: install/remove re-materialization remapped the seq of an old otadata boot request to a drifted slot, causing reset loops recoverable only by erasing otadata. Table rewrite now invalidates stale boot requests immediately.

## New capabilities

- **Store list shows true storage footprint**: the list used to carry only the bare firmware download size, badly understating plays with DATA reservations (Morse Code Trainer: 4.9 MB download, 7.8 MB true need). The worker stores analyze's requiredSize in a KV summary cache (key includes the firmware sha256 — an update naturally invalidates, no TTL), the `/api/plays` proxy enriches every item, and cold entries backfill in the background; list cards and the detail page show "total needed (incl. DATA reservation)". too-large rejections carry the real numbers vs pool limit.
- **Capture data upload**: pass-radar batch-capture bytes travel from the phone page straight to the ingest endpoint (`POST /api/capture/ingest`); device identity is proven by the cardid hash stamped in the RCB1 batch header — the plaintext never leaves the device; the storage-management panel shows the upload section only when an installed play owns capture records.

## Flashing

`meta-pass_v2.3.0.bin` is the dual-use single-file format (bootable body + MPUPV2 trailer):

- **Fresh flash / unbrick**: write the whole image with the online flasher → <https://ai-passport.folotoy.cn/tools/web-flasher/>;
- **Normal upgrade (slots and data preserved)**: OTA / store channel in the device launcher recognizes the MPUPV2 trailer.

## Verification

- Firmware builds with 0 errors; boots clean on the real device (carve record, WiFi, store page all normal).
- Install chain: real store firmware (Pocket Radar 446 / Radar Hide & Seek 351) through the full preflight → prepare → upload → finalize → done flow; all three most common 401 reasons verified on-device with their distinct messages.
- Truncation fix: parser, `esptool image_info`, and length/SHA agree three ways (176B → 2,321,984B).
- List enrichment: 0/20 → 12/20 convergence observed round-over-round on production Pages; Morse Code Trainer 1134 shows 7.8M in the list.
- Known pre-existing: two CI "Static checks" cases have been failing on pristine HEAD since 2026-10-26 (host stubs and worker contract tests); firmware artifacts unaffected.
