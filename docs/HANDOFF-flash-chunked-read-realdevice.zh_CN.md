# Handoff｜feat/storage Flash 分块读取真机验证

日期：2026-10-13  
目标分支：`feat/storage`  
适用提交：交接执行时的最新 `origin/feat/storage` HEAD；不得沿用旧提交的 PASS。

## 1. 目标

验证 Flash 长距离读取是否能通过有限大小的分块及周期性串口会话重建，避免 Chrome Web Serial / esptool-js 持续读取数分钟后挂起。此次修复目标是**读取和读回校验**，不是分块写入优化。

当前实现预期：
- 单次 Flash read 最大 32 KiB。
- 每累计读取 512 KiB，关闭并重新打开当前串口 transport、清空接收缓冲并重新同步，再继续读取。
- APP 和 DATA 的读回都走同一分块读取/逐字节比较模块。
- 短读、非法长度、任意字节不一致均必须失败关闭，不能报告验证成功。
- 原有 Flash 擦除与写入流程保持不变。

## 2. 开始前的门禁

在本地仓库执行并记录真实输出：

```bash
git checkout feat/storage
git pull --ff-only origin feat/storage
git status --short
git rev-parse HEAD
./tools/validate.sh
```

确认当前 HEAD 的 Static checks 和 Firmware checks 均通过，并记录固件 SHA-256、设备标识（可脱敏）、浏览器/OS、ESP-IDF、Node 版本、串口端口及页面入口。若工作区不干净、commit 不匹配、构建或宿主测试失败，先停止并报告，不要开始破坏性真机操作。

## 3. 测试步骤

### R0 — 基线与连接稳定性
1. 记录当前设备 APP/DATA 清单和 Flash 空间状态。
2. 确认设备、串口、配对和页面版本正确。
3. 记录读取前后的设备状态；不要为此测试移动 cardid、硬编码 Flash 地址或改变固定分区布局。

### R1 — APP 长距离读回
1. 使用本次构建的 USB 服务页面安装或选择允许测试的 APP 镜像。
2. 触发 APP 写后读回校验；保留页面日志及串口连接事件。
3. 确认读取按不超过 32 KiB 的块推进，累计到 512 KiB 时确实发生 disconnect → connect → sync。
4. 确认所有块连续覆盖目标范围，无地址跳跃、重复或遗漏；最终逐字节比较通过。
5. 对超过 512 KiB、最好超过数 MiB 的 APP 镜像执行测试，以覆盖多个会话边界。

### R2 — DATA 长距离读回
1. 在允许测试的 APP/DATA 场景中触发 DATA 写后读回校验。
2. 同样检查每块长度、偏移连续性、512 KiB 会话边界及逐字节校验结果。
3. 使用多 MiB DATA 覆盖多个重连边界；记录每次重连耗时、是否超时以及是否需要人工恢复连接。
4. 确认 DATA 读回成功后，APP/DATA 清单及分区范围未发生非预期变化。

### R3 — 失败关闭与恢复
在安全的测试/宿主层验证短读、字节不匹配、读取异常和重连/同步失败都会明确报错。若真机自然出现上述失败，保存现场，不要通过跳过校验或 `?noverify` 将其改记为 PASS。

### R4 — 备份/恢复回归（仅在设备和数据允许时）
1. 先确认有可验证备份，并遵守现有备份/恢复 handoff 的所有人工确认门禁。
2. 验证页面的长距离 APP/DATA 读回不再在持续读取阶段挂起。
3. 若执行恢复，分别记录写入、读回验证、事务提交和最终清单；不得把恢复写入成功当作读回校验成功。
4. 真实市场 28 号玩法每次安装或恢复后，必须停下并等待人工确认实际 DATA 可读、可写、重读值正确；未确认保持 `BLOCKED_WAITING_FOR_HUMAN_DATA_CONFIRMATION`。

## 4. 通过标准

- APP 和 DATA 长距离读取均完成，且每个读取块不超过 32 KiB。
- 每 512 KiB 边界的串口重新连接与同步有日志证据，后续读取能继续。
- 读取范围连续、无短读、无遗漏；逐字节比较和相应 hash 校验通过。
- 多次重连后无永久挂起、无未解释超时，页面能给出最终成功/失败状态。
- 现有擦除/写入路径未被意外改成新的分块写入实现。
- 测试报告注明当前 commit、固件 hash、环境、APP/DATA 尺寸、块数、重连次数、耗时、校验结果和未覆盖项。

## 5. 失败取证与归因

失败时立即停止后续破坏性操作，保留：
- 完整页面日志、浏览器控制台错误和可获得的 UART 日志；
- 读取地址、请求长度、实际返回长度、块序号、累计字节数；
- disconnect/connect/sync 的时间戳、耗时、异常与重试情况；
- 设备 APP/DATA 清单、当前 commit、固件 SHA-256；
- 自动化报告与实际执行命令/退出码。

初步归因：
- Host test 失败：分块算法或测试问题。
- 块偏移不连续、短读或字节不一致：读取协议、缓冲区或地址计算问题。
- 重新连接/同步失败：transport 生命周期、stub/loader 会话或串口恢复问题。
- 仅长时间读取挂起而短读取通过：仍未解决的持续读取/会话稳定性问题。
- 设备重启、panic 或分区范围异常：固件/设备问题；保留现场并停止。

不要通过放宽校验、跳过读回或伪造重连日志来通过测试。

## 6. 交付报告

报告至少包含：
- 测试时间、分支与完整 commit SHA；
- 固件 SHA-256、设备/固件类型、OS/浏览器/Node 版本；
- APP/DATA 的字节数、块数、512 KiB 边界数和重连次数；
- 每阶段耗时、错误/重试、逐字节校验及 hash 结果；
- 页面/UART/浏览器日志与报告路径；
- 结论：PASS / FAIL / BLOCKED，以及明确的失败归因；
- 是否完成真实市场 28 号玩法的人工 DATA 确认。未确认不得标为 PASS。

CI 通过只是进入真机测试的前置条件，不代表本 handoff 的真机验收已通过。
