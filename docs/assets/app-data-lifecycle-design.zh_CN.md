# APP 与 DATA 生命周期设计（feat/storage）

## 1. 目标与范围

第一版优先保证行为可解释、生命周期闭合和故障后可恢复，不引入孤儿 DATA、跨安装实例自动重关联或独立 DATA 管理流程。

核心规则：

1. 每次安装 APP，都从动态回收池分配新的 APP carve；不复用旧 APP 槽位作为逻辑身份。
2. 一个 APP 安装实例拥有自己的 DATA 集合。默认不允许跨 APP 共享可写 DATA。
3. **卸载 APP 必须同时删除该 APP 关联的全部 DATA；不提供单独删除 DATA 的用户操作。**
4. 若需要保留数据，用户必须在卸载前备份；卸载后重新安装属于新的安装实例，用户通过恢复备份迁移数据。
5. 不允许残留孤儿 DATA，也不提供卸载后重新关联旧 DATA 的机制。
6. 物理 slot/offset 只是当前分配位置，不是持久身份；释放后可由池分配器分配给其他对象。

## 2. 身份与关联

- `play_id`：玩法/APP 的逻辑标识，用于识别某玩法拥有的资源。
- `install_id`：每次成功安装生成的安装实例标识，用于避免同一玩法重装时误认旧数据。
- `data_id`：一组逻辑数据的标识；同一 APP 可有多个按 label 区分的 DATA 分区。
- `label`：DATA 分区在 APP 内的稳定用途名，例如 `save`、`assets`。

关联必须明确指向安装实例；若现有持久化格式暂时只有 `play_id + label`，应在实现中把它标为迁移限制，不能把 slot/offset 当替代身份。没有可靠的实例关联时，不应猜测并删除其他 APP 的 DATA。

## 3. 卸载流程

卸载前先将目标 APP 的 play_id、offset、size 写入 NVS 并提交，作为持久化删除意图。擦除 DATA 字节与 APP 镜像头后，再通过一次 A/B carve 提交同时移除 APP 和所有关联 DATA 记录；只有提交成功后 extents 才能回到回收池。启动本地管理服务时会检查未完成的删除意图，按 play_id + offset + size 重新定位目标并幂等续做，绝不只凭旧 slot 下标删除对象。若旧 APP 的 play_id=0 且池内存在 DATA 记录，系统拒绝卸载，因为无法安全证明这些 DATA 的归属。

卸载是一项不可逆的级联删除操作。UI 只提供一个明确的“删除 APP 及其数据”动作，不展示单独删除 DATA 的控件，也不允许通过取消某个 DATA 项来部分卸载。

推荐状态机：

1. **PRECHECK**：拒绝与安装/恢复会话并发；读取 APP 和所有关联 DATA 的完整清单；验证记录和范围都在池边界内。
2. **BACKUP NOTICE**：当前已可导出真实 APP/DATA 字节，但尚未实现导入恢复。必须明确告诉用户 ZIP 可以保存字节、却暂时不能通过产品恢复；用户明确确认永久删除后才能继续。
3. **DELETE_INTENT**：先持久化卸载事务记录，包含目标 APP、关联 DATA 清单、事务 ID 和阶段；写入并校验成功后才开始擦除。
4. **ERASE DATA**：逐个擦除关联 DATA 的实际 Flash extent；每个 extent 擦除后校验。保留可恢复的事务进度，重启后继续处理。
5. **ERASE APP HEADER**：擦除 APP 镜像首扇区，避免重启扫描将已删除 APP 重新识别为有效镜像。
6. **COMMIT**：在单个可恢复的持久化提交中移除 APP 与其全部 DATA 记录，更新分区表/池记录并验证。
7. **RECLAIM**：只有提交状态确认不再引用这些 extent 后，才将空间返回动态回收池。
8. **DONE**：清除事务记录，返回成功。若任一步失败，保留事务记录并在下次启动时继续或进入明确的恢复错误状态；不得报告成功，也不得把仍被记录引用的空间重新分配。

### 原子性与崩溃恢复

Flash 擦除无法物理回滚，因此“原子”指逻辑上的可恢复提交，不意味着擦除期间内容仍可恢复。持久化事务意图必须先于破坏性操作。恢复代码必须幂等，能处理重复擦除、提交已完成但事务标记尚未清理等情况。

严禁以下顺序：
- 先释放空间，再擦除旧内容或移除所有引用；
- 先删除 APP 记录、后异步尝试清理 DATA，却没有持久化事务；
- 擦除失败仍移除记录并返回成功；
- 仅清记录但保留可被启动扫描识别的 APP 镜像头。

## 4. DATA 删除与调整

- 不提供单独删除 DATA 的用户入口。
- 不允许用户选择卸载时保留 DATA；APP 删除必然级联删除。
- 若某 APP 有多个 DATA 分区，全部属于同一卸载事务。
- DATA 容量由用户在安装/分区配置流程中选择允许范围内的大小。
- 扩容采用迁移式流程：先分配临时 extent、复制并验证内容，再原子切换引用，最后释放旧 extent。
- 缩容只有在具体 DATA 格式支持安全缩容迁移并完成验证时才开放；否则禁用。
- DATA 数量受全局记录上限与池容量共同约束；第一版不支持跨 APP 共享。

## 5. 备份与恢复

完整备份必须包含真实 DATA 字节，而不只是 offset/size/state/label 元数据。建议归档至少包括：

- 格式版本、校验和；
- `play_id`、源 `install_id`、固件/数据格式版本；
- 每个 DATA 的 label、类型、原始逻辑大小、格式信息；
- 实际数据字节及每个对象的 SHA-256。

归档不得依赖源设备的 slot 或 Flash offset。恢复时先验证整个归档的结构、长度与校验和，分配新的 extents，写入并逐项校验后，再一次性提交 DATA 记录；失败时释放尚未提交的新 extents。恢复目标必须明确为同一逻辑 APP，且目标固件/数据格式兼容。

**当前实现边界：**USB 与手机页面现已可将真实 APP 槽位和关联 DATA 字节导出为 MPTB v2 ZIP，并执行 SHA-256 校验。导入/恢复及原子暂存写入事务仍未实现。UI 不得暗示当前可通过产品恢复已导出的归档。

## 6. 并发、容量和安全不变量

- 安装、卸载、恢复和容量迁移互斥；同一时间只允许一个改变池布局的事务。
- 任意 DATA extent 必须完全位于 DATA pool 内，且不得与 APP、其他 DATA 或保留区重叠。
- 记录引用的 extent 不得回收；未提交的新 extent 不得暴露为有效 DATA。
- 只有所有关联 DATA 与 APP 的引用均已删除且提交完成后，才可把空间视为可用。
- 槽位编号和物理 offset 变化不得改变 APP/DATA 的逻辑关联。
- UI 成功提示必须来自设备端提交结果，而非本地按钮状态或 toast。

## 7. 验收标准

1. UI 不出现单独删除 DATA、保留 DATA 或归档孤儿数据的选项。
2. 删除 APP 时，设备端枚举并删除该 APP 的全部 DATA，包括多个 label。
3. 删除成功后，APP 与 DATA 记录都不存在，关联 extent 不再被引用，池容量增加量与实际释放范围一致。
4. 删除失败时不返回成功；失败后不得把仍被记录引用的空间分配给新 APP/DATA。
5. 删除中断后重启，事务可幂等恢复；已删除 APP 不会被镜像扫描复活。
6. 删除其他 APP 不得影响其 APP、DATA 字节或记录。
7. 新安装使用新 carve；需要旧数据时，只能通过完整备份恢复。
8. UI 支持完整单 APP+DATA v2 归档恢复；多 APP 原子恢复和全局 NVS 恢复暂不支持。恢复必须先校验归档完整性与 SHA-256，再通过设备安装事务提交，绝不接受客户端 Flash 地址。
9. Host 测试覆盖正常删除、多 DATA、擦除失败、提交失败、重复恢复和记录/extent 一致性；真机验证另行记录，不能以 host 测试替代。

## 8. USB 服务页与手机内嵌页的功能对齐

USB 服务页与手机内嵌页是同一套存储管理能力的两个入口，不能形成两套业务语义。设备端 API、carve 记录格式、DATA 归属、大小约束、删除事务、备份归档格式和恢复提交规则必须共用；入口差异只允许来自连接方式和能力范围。

| 能力 | 手机内嵌页 | USB 服务页目标 |
|---|---|---|
| 已安装 APP / DATA 清单 | 支持 | 对齐同一设备清单与归属信息 |
| 安装 APP | 市场/远程固件 | 市场/远程固件 + 本地固件文件 |
| DATA 大小选择 | 支持受约束的用户选择 | 同样支持，使用同一范围、步长和最小值规则 |
| 删除 | 删除 APP 并级联删除其全部 DATA；不提供独立 DATA 删除 | 完全一致，不允许仅删除 DATA 或保留 DATA |
| 备份 | 必须归档实际 DATA 字节并校验 | 使用同一归档格式与字节校验，不得退化为只备份元数据 |
| 恢复 | 校验归档、分配新 extent、写入验证后提交 | 使用同一恢复事务；不能复用源设备的物理 offset |
| 失败恢复 | 不谎报成功，保留可恢复状态 | 同样遵循，不因 USB 下载模式绕过事务约束 |

### 8.1 本地固件安装的专属扩展

USB 页允许用户选择本地 Full Flash 固件文件。安装流程应复用与远程安装一致的镜像解析、分区清单验证、APP/DATA 规划、容量校验和 DATA 大小约束，不得只提取 factory APP 而忽略同一固件声明的 DATA 分区。

执行顺序必须保证不会产生孤儿或错误归属：

1. 读取并验证本地镜像；解析 factory APP 与全部可支持 DATA 声明，拒绝未知的自定义 DATA subtype，除非其已被明确注册为受支持的原始 DATA 类型。
2. 校验 label、subtype、分区尺寸、镜像内偏移/范围、DATA 数量、重复声明、保留分区冲突和池容量。
3. 读取当前 carve；为 APP 和全部 DATA 生成完整提案。提案须同时考虑现有 APP 与 DATA 占用，且与设备端分配器规则一致。
4. 对需要覆盖的已有 APP 实例执行显式确认；不得默默覆盖其他 APP 或复用其 DATA。
5. 先准备可恢复的安装事务与分配记录；写入 APP/DATA payload 后逐项读回校验。若任何步骤失败，按事务记录恢复旧状态或继续回滚，不能留下有效但不完整的 APP/DATA 组合。
6. 只有全部 payload 验证通过后，才提交 APP 与 DATA 的最终记录及分区表；成功提示必须以设备可验证的提交结果为准。

若现有记录格式只能用 `play_id + label` 关联 DATA，必须在 USB 本地安装路径中显式写入可靠的 `play_id`，并遵守“同一 APP 安装实例拥有其 DATA”的限制。不能从文件名推测身份，也不能因 APP 删除后仍保留 DATA。

### 8.2 USB 本地固件 DATA 镜像的处理规则

- Full Flash 镜像中 DATA 分区的声明和 DATA 初始 payload 是两回事；必须分别校验，不能把声明大小误当成镜像里一定包含完整初始数据。
- 只接受明确支持的 subtype。NVS/PHY/OTA 元数据及 `cardid`、`store` 等固定系统分区不是子固件 DATA，不能被 carve 或覆盖。
- 当前 `cardid` 的物理位置必须保持不变；不得通过移动固定分区来解决 DATA 容量不足。若合法池空间无法容纳某 DATA，安装应清楚失败并报告最大连续空间，而不是越界或改变固定分区布局。
- 对只用于原始读写测试的自定义分区类型，必须在固件解析器、DATA 记录和测试协议中明确注册；不得把所有未知 subtype 一概当成可写原始 DATA。

### 8.3 验收补充

10. USB 与手机对相同设备状态呈现相同的 APP/DATA 归属和容量；两个入口的删除结果、备份归档内容和恢复结果可交叉验证。
11. USB 本地 Full Flash 安装能同时安装 APP 与其声明的 DATA；遇到不支持 subtype、容量不足、重复 label 或镜像越界时，在破坏设备内容前拒绝。
12. APP 写入成功但 DATA 写入失败、DATA 写入成功但最终提交失败、设备断开或页面刷新等故障注入场景均不得留下可启动但缺少其 DATA 的已提交实例。
13. 备份可由任一入口创建，并由另一入口恢复；归档包含实际字节及 SHA-256，恢复后的内容逐字节一致。
14. USB 和手机共用同一套生命周期合同测试；UI 冒烟测试只验证交互，不能替代设备端事务和字节级校验。
