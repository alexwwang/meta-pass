# 通用 DATA 分区大小调整方案

状态：设计与实施基线（feat/storage）

## 1. 目标

把 DATA 分区容量从测试任务中的固定参数提升为安装流程中的通用能力。任何符合动态分区协议的子固件，在安装时都可以申请 DATA 分区；用户在手机内嵌安装页面中明确选择容量，设备端按统一规则校验、分配、持久化和激活。

本能力不得依赖特定 Play ID、测试任务名称、测试开关或“空白 FAT”假设。未申请 DATA 分区的旧固件仍按原流程安装；不支持动态 DATA 的设备/固件必须给出明确提示，不能静默回退成错误容量。

## 2. 设计原则

1. **通用策略与测试隔离**：生产逻辑不识别测试任务；测试只负责覆盖通用 API 和边界。
2. **容量由用户决策，设备负责最终裁决**：UI 展示设备能力范围，提交后仍由设备重新校验，不能信任前端参数。
3. **不破坏已有数据**：调整已存在的 DATA 分区可能造成格式化/截断，默认不自动缩小、不覆盖已有分区。
4. **单一容量语义**：统一以字节作为协议和存储层单位；UI 用 MiB 展示。所有大小在边界处明确换算。
5. **原子提交**：只有 APP 槽位和 DATA 分区布局都校验成功后，才提交 carve 记录并物化活动分区表；失败时保留原布局。
6. **兼容旧固件**：无 DATA 申请字段视为“无额外 DATA 分区请求”，维持既有行为。

## 3. 用户流程

1. 手机端解析并校验固件镜像，读取固件的安装能力声明（例如是否需要 DATA、支持的最小/最大值及推荐值）。
2. 若固件支持 DATA，页面显示“数据分区大小”选择器：包含设备可用范围、步进和推荐值，并显示选择后剩余可分配空间。
3. 用户选择容量后，页面把规范化的字节数随安装 offer 提交给设备。
4. 设备端根据当前 flash carve 状态、固件 APP 需求、DATA 分区对齐规则和保留区重新计算可用容量；拒绝非法或超范围请求，并返回允许范围及原因。
5. 用户确认后，设备按事务流程完成分配；上传、镜像校验、容量校验或提交任一步失败都不得留下半提交布局。
6. 安装完成后，启动目标固件前物化与该固件关联的 DATA 分区；其他固件不应看到或误用此 DATA 分区。

## 4. 容量范围与 UI 规则

范围不能硬编码为某个测试任务的固定值。由设备当前布局和通用配置共同决定：

- min_size_bytes：通用下限，至少满足文件系统/应用元数据的最小可用容量，并按 DATA 分区对齐粒度向上取整。
- max_size_bytes：当前可分配空间扣除 APP 槽、固定保护区、carve 元数据/对齐损耗后的最大连续容量，并按对齐粒度向下取整。
- step_bytes：用户选择步进，默认 1 MiB；最终仍需按分区表要求对齐。
- recommended_size_bytes：固件声明的建议值，必须落在设备返回的合法范围内，否则忽略并回退到合法默认值。
- UI 展示 min–max MiB、步进、当前选择和选择后的剩余空间；max 小于 min 时禁用安装并解释原因。
- UI 只展示设备确认的有效范围。前端先行计算只能用于预览，不能作为安全边界。

建议第一版采用 1 MiB 步进；具体 min/max 不写死为某个固定范围，而由设备能力响应动态给出。配置项需有统一默认值和单元测试，不应散落在页面、协议和 carve 模块中。

## 5. 协议与数据模型

扩展安装 offer/会话快照，增加可选 DATA 需求信息，建议字段：

- data_partition_required：boolean
- data_size_min_bytes：uint32
- data_size_max_bytes：uint32
- data_size_recommended_bytes：uint32
- data_size_selected_bytes：uint32（用户选择后才存在）
- data_size_step_bytes：uint32

设备对页面返回能力/范围，页面提交所选字节数；字段缺失表示旧固件，不得把缺失值解释成 0 字节 DATA 分区。字段必须经过严格类型、范围、溢出和一致性检查。若现有协议已有等价字段，应复用而不是引入重复语义。

固件能力声明必须来自可验证的镜像元数据/manifest，而不是从 Play ID、URL、文件名或测试标志推断。若当前格式尚无正式能力声明，第一阶段可以由通用 manifest/offer 承载，明确版本号并对未知版本 fail closed。

## 6. 设备端分配与提交

建议复用现有 meta_carve / meta_carve_flash 的动态布局能力，不新建第二套分区分配器。

1. **Prepare**：验证目标 APP 槽、请求容量、对齐、剩余空间及保护区不重叠；生成待提交布局。
2. **Reserve**：把 DATA 分区作为与 APP/Play 关联的 carve 记录，验证分区标签唯一、地址和长度合法。
3. **Write**：按既有 OTA 流式写入 APP；不因 DATA 选择把整份固件缓冲到 RAM。
4. **Validate**：验证 APP 镜像长度、芯片类型、结构和摘要；再次验证 DATA 布局。
5. **Commit**：持久化完整 carve 记录后再更新活动分区表。记录采用已有双副本/校验/序号机制（若现实现不具备，则先补齐原子提交能力）。
6. **Activate**：启动对应 APP 前，只物化该 APP 关联的 DATA 分区视图。
7. **Rollback**：任一步失败都恢复上一次已提交记录；不得删除或覆盖其他固件的 DATA 数据。

DATA 分区初次创建时可由应用按自己的文件系统策略格式化。改变已存在 DATA 分区大小属于破坏性操作：第一版只允许新建时选择大小；若要调整既有分区，必须提供备份/迁移或明确擦除确认，绝不静默截断或重格式化。

## 7. 兼容性与错误处理

- 旧 offer/旧固件：不请求 DATA 时行为保持不变。
- 不支持动态分区的固件/设备：禁用选择并显示原因，不允许客户端绕过。
- 请求小于最小值、大于最大值、未按步进、整数溢出、标签冲突或空间不足：设备拒绝并返回机器可读错误码及合法范围。
- 安装中断：不得提交新 carve 记录；半成品 APP 按现有失败清理策略处理。
- 重新安装同一 Play：若已有 DATA 分区，默认保留其大小和内容；新选择与现有布局冲突时要求用户明确选择保留/备份后重建，不能静默覆盖。
- 固定保护区域（尤其 cardid）始终不可分配；所有计算必须使用设备实际 flash size 和已读取的设备分区表。

## 8. 测试驱动实施计划

### 阶段 A：先补纯逻辑测试

- 容量单位转换、最小/最大值、步进和分区对齐。
- 刚好等于 min/max、低于 min、高于 max、空间刚好耗尽、剩余不足一个 step。
- 32 位溢出、负数/非整数输入、缺失字段、未知协议版本。
- APP 与 DATA 的地址/大小不重叠；保护区与 carve 元数据不被覆盖。
- 旧 offer 不含 DATA 字段时行为不变。

### 阶段 B：设备端通用 API

- 在 carve/安装模型中增加纯逻辑的容量规划 API。
- 安装 offer 返回设备能力与范围；设备端在确认时再次校验。
- 事务式提交/失败回滚；按 APP 关联 DATA 分区并在启动前物化。
- 删除 Play/槽位时，明确 DATA 生命周期；默认不自动删除含用户数据的 DATA 分区，除非现有产品策略已明确要求级联删除并二次确认。

### 阶段 C：手机内嵌页面

- 增加通用容量选择器、范围/步进/推荐值、剩余空间提示和校验错误展示。
- 页面只消费设备/manifest 提供的能力，不含 Play ID、测试任务或特定固件名称分支。
- 语言切换时动态文案同步更新；小屏布局可滚动且选择器不遮挡确认按钮。

### 阶段 D：端到端验收

- ./tools/validate.sh --static
- node tools/install-slot/test-extract.mjs 及相关页面测试
- ./tools/validate.sh --firmware
- 浏览器测试：范围显示、步进、边界拒绝、旧固件兼容、语言切换。
- 真机测试：选择不同容量安装、重启后分区可见、写入/读取数据、重新安装保留数据、空间不足和断电失败恢复。
- 检查生成分区表及最终镜像，确认 cardid、NVS、otadata 等保护区域未被覆盖。

## 9. 完成标准

- 生产代码中不存在按测试任务/Play ID 开启 DATA 容量选择的门禁。
- 用户能在手机页面选择设备当前允许范围内的 DATA 大小。
- 设备端独立校验并原子提交；非法值不能造成布局损坏。
- DATA 分区与固件实例关联，启动时可见且互不串用。
- 旧安装流程兼容，已有 DATA 内容不会被静默擦除。
- 静态测试、宿主测试、固件构建、浏览器测试通过；真机分区读写和重启验证通过。

## 10. 决策记录

- 2026-10-10：DATA 容量选择属于动态存储的通用能力，不属于特定测试任务。容量由用户选择，设备按当前布局动态提供合法范围并做最终校验。
- 2026-10-10：第一版仅在创建 DATA 分区时允许选择大小；对既有分区的缩放/重建必须作为显式破坏性迁移处理。

## 11. 实施进度（2026-10-10）

- 已在 `install-slot/dynslot-pool.js` 增加通用 DATA 容量范围计算与容量值校验：考虑现有 APP/DATA 占用、64 KiB 起始地址对齐、4 KiB 大小粒度；异常重叠布局不提供可分配容量。
- 已在 `install-slot/phone-install.js` 增加安装确认前的通用 DATA 容量选择步骤；不依赖 Play ID 或测试任务开关。新建 DATA 的最小容量按已知文件系统类型与内嵌 payload 计算：空白 FAT 保守下限 1 MiB，空白 SPIFFS/LittleFS 下限 64 KiB，含内嵌 payload 或未知类型保留 manifest 声明容量。
- 已存在且满足最低容量的 DATA 保留原容量，不在此流程中缩小或覆盖。选择多个 DATA 时会验证所选容量组合；空间不足、坏几何和跨池/池外占用 fail-closed。
- 已在 `tests/test_dynslot_pool.mjs` 增加容量范围、4 KiB 对齐、边界值、APP 占用、已有 DATA 占用、重叠/非法/池外几何 fail-closed 测试。
- 2026-10-10 存储策略更新：每次安装必须创建新的 APP carve，不允许复用既有 APP 槽位；DATA 容量选择在新 APP carve 的安装流程中完成。设备 prepare 端拒绝不带 carve 提案的旧式安装请求。
- CI 状态需以包含 fresh APP carve 策略的最新提交为准。此前提交的静态/宿主测试与固件构建结果不能代替本次改动的 CI；浏览器和真机仍需按新的“安装新槽—删除释放—再次安装”语义验收。不得将旧真机报告视为该策略已通过。
