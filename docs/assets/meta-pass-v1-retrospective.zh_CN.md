# meta-pass v1.0.0 开发之旅 —— ELI5 回顾

> 状态:阶段回顾(2026-09-13 → 2026-09-18,feat/sign 分支合入 main 并发布 v1.0.0)。
> 读者:任何想了解"这东西是怎么做出来的、踩了哪些坑"的人,包括未来的我们自己。
> 技术细节的权威版本在 [设计文档](meta-pass-design.zh_CN.md) 与
> [签名设计](meta-pass-signing-design.zh_CN.md);本文用大白话讲清楚来龙去脉。

## 一、我们要做什么(目标)

想象一台只能跑"一个程序"的玩具电脑(AI Passport)。我们想把它变成一个
**能装好几个程序的小盒子**,而且要好玩、安全、折腾不坏:

1. **一个开机菜单(meta-pass 启动器)**:开机先看到列表,选中哪个程序就玩哪个;
2. **三个抽屉(槽位)**:最多装 3 个玩法固件,随时换、随时删,互不干扰;
3. **官方认证贴纸(签名)**:官方认可的固件贴一枚"火漆印"(签名 + 名字),
   来路不明的固件开机前会先警告你;还能给固件加一个"开机小惊喜"(彩蛋);
4. **搬家打包(备份/还原)**:把盒子里所有东西(固件 + 数据)拍快照存成一个
   zip,换机器、重刷机之后一键放回去;
5. **升级不丢东西**:升级"菜单程序"本身时,你的玩法固件和数据一个都不能少;
6. **每次开机回菜单**:玩完(甚至断电重启)永远回到菜单,不会卡死在某个玩法里。

## 二、方案是怎么做的(用类比讲)

### 槽位 = 一排抽屉

Flash 里划出三个大小不一的"抽屉"(ota_0/ota_1/ota_2)。每个抽屉里放:
**固件本体** + 抽屉最底下的**一页贴纸(4KB 元数据扇区)**——签名、玩法名字
都写在这页纸上。启动器每次开机就是把三个抽屉看一遍,把清单画在屏幕上。

### 签名 = 只有官方才有的印章

我们有一对"钥匙":私钥只有发布者有,公钥谁都可以拿着比对。发布固件时用
私钥在贴纸页上"盖个章";设备上的启动器拿公钥验章——花纹对得上,就显示
签名徽章和名字。配套工具链 `sign-firmware.sh` 还能往贴纸页塞一段"彩蛋文字",
并支持 `--check-egg-text` 提前检查长度是否放得下。

### 单文件固件 = 一个汉堡

以前发版要三个文件(完整镜像/升级容器/出厂镜像),用户容易拿错。
现在只发**一个文件**:汉堡胚(bootloader)+ 生菜(分区表)+ 肉饼(应用)
叠好,最后再插一根 44 字节的"小牙签"(MPUPV2 版本指纹):

- **市场全新安装**:整只汉堡原样塞进 Flash 的 0x0 位置(小牙签落在肉饼后面
  的空地上,启动器不理它,引导完全正常);
- **网页保数据升级**:配套网页认识这根牙签,把汉堡拆开,只换胚、菜、肉饼,
  **不碰**你的"小本本"(NVS)和三个抽屉——这就是"保数据升级";
- 一套校验器(`tools/validate.sh`)盯着:发出去的汉堡必须内外一致。

### 备份/还原 = 搬家前拍照 + 打包清单

每个抽屉拍最多三张照:**固件本体**、**额外存的数据**、**贴纸页**;全部照片
算一遍指纹(SHA-256)写进**一张清单**(manifest.json),最后装进一个 zip。
搬家(换机/重刷)时:

- 新家抽屉比旧家小?看清单里每张照片的长度,放得下才动手,放不下就明确拒绝
  ——绝不写一半把你数据切烂;
- 照片和清单上的指纹对不上?拒绝使用——防止搬运路上损坏;
- "小本本"(NVS,Wi-Fi 密码、应用笔记)也**自动**拍一张放进包里、还原时
  **自动**写回——用户不需要懂什么是 NVS,也不用做选择。

### 每次开机回菜单 = 看门人在游戏开机前动手

这是本期**最重要的架构决策**。第一版方案是"请玩法固件自己守规矩":别去按
那个"我要常驻"的确认按钮(otadata 写 VALID)。但旧玩法固件是按老规则编译的,
照样会按——菜单根本没机会管。

最终方案:在**比所有程序都早**的阶段安排一个看门人(2nd-stage bootloader
hook)。每次上电,看门人先瞄一眼"预约表"(otadata),只要发现有"常驻"标记,
**直接擦掉**,然后照常把选择权交回菜单。效果:

- 无论玩法固件守不守规矩、是旧版还是新版,开机必定回菜单;
- 曾被玩法"锁死"的设备,升级后重启一次就自愈;
- 玩法固件什么都不用改——开机策略从此**由 meta-pass 单方面决定**。

## 三、过程中的坑与教训(最有价值的部分)

### 技术类

**教训 1:关键策略不能依赖"参与者自觉"。**
单次会话最初靠玩法固件侧的 hook 模板"不写 VALID"实现,而玩法仓库里那份
模板拷贝一直是旧版——策略静默失效。规则:凡是系统级约束,必须由系统自己
在不可绕过的层(bootloader)执行,不能指望每个参与方都配合。

**教训 2:"编译通过" ≠ "功能在里面"。**
bootloader hook 第一次编译全绿,但检查二进制发现 **hook 根本没被链接进去**
(新建组件目录不触发 cmake 重新配置;组件还缺 CMakeLists.txt)。靠 map 文件
和日志字符串搜索才抓到。规则:交付前要找"它确实在产物里"的直接证据,而不是
"没报错"。

**教训 3:读取慢/失败,先怀疑协议,别怪硬件玄学。**
浏览器备份功能最初 1MB 要读三分钟、频繁报错。对照 esptool.py 官方实现逐条
排查后发现三件事:校验帧(MD5 digest)没读、每个数据帧缺 ACK、块太小。
对齐官方"停等"节奏 + 提到 921600 波特率后,速度提升一个数量级,失败率断崖式
下降。规则:造轮子前先逐行读久经考验的同类实现。

**教训 4:测试必须能在"和 CI 一样的裸环境"跑。**
有一个测试直接读本地 `build/` 目录的构建产物做比对,本地全绿、CI 一跑就崩
(裸 checkout 没有 build/)。改成"有产物跑真比对、没产物用合成数据跑同一套
逻辑断言"的双模式。规则:静态门禁不允许隐式依赖本地环境。

**教训 5:注释里的一个反斜杠能炸掉整条 CI。**
`//` 注释行尾带 `\`,编译器会把下一行吞进注释,`-Werror` 直接报错——而且是
存在一周多才被发现的老问题。同类问题一次扫出两处。规则:门禁要常跑;修一个
之后全局扫同类。

### 流程类

**教训 6:线上版本 ≠ 仓库版本,要给一切打版本戳。**
排查"签名验证不上"三天,最后发现线上安装页是旧版本。现在:固件带 git hash
版本戳,网页日志首行显示部署时的 git SHA,门禁守护版本占位符——一眼对账。

**教训 7:工具链的"发布链"要亲自完整走一遍。**
`validate.sh` 曾同时存在:文件名 glob 不匹配、固件没有落盘到发布目录、被截断
的中文注释被 bash 当命令执行——单步都对,链路断。规则:改完工具链,从头到尾
跑一遍真实发布流程才算验收。

**教训 8:一次性资源,先验证落点再动手。**
发布授权码是一次性的,第一次兑换因为配置文件路径写错,码被服务端消费却没存
下来,只能重发。规则:不可逆操作前,先把整条命令的每个参数核对一遍(干跑)。

### 协作类

**教训 9:先对齐词汇,再解决问题。**
"详情页"和"启动确认页"指的是同一个东西,一方以为是另一页,来回空转。
规则:对话里出现两个叫法,先确认指的不是两个东西。

**教训 10:说人话。**
用户明确要求"不要隐喻、不要副词修饰"时,把因果链直接摆出来:做了什么、
为什么、证据是什么。技术写作默认克制形容词。

### 工程习惯(贯穿本期)

- **静态分析先行**:每次改完先自查(grep/map 文件/语法检查),再请用户验收;
- **真机证据 > 推断**:设备屏幕闪没闪、串口日志有没有那行字,比"应该可以"可信;
- **双语文档同步**:每个正式文档英文 + 简体中文成对维护,改一处必改另一处;
- **commit 里不写 AI 署名**:仓库历史曾为此专门重写过一次,不再引入。
