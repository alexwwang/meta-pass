# meta-pass Child Firmware Signature Badge — Standard Design

> 简体中文: [meta-pass-signing-design.zh_CN.md](meta-pass-signing-design.zh_CN.md)
>
> Status: standard contract. All implementations align to this design; any drift is a defect.
> Basis: docs/assets/meta-pass-design.md §6/§7, historical fix commits (ea21e03 → dbbd091 → 325d01f → aa25c52 → 9d9fc98),
> authoritative ESP-IDF v5.5.3 semantics (components/bootloader_support/include/esp_app_format.h, src/esp_image_format.c),
> docs/BUGS.md.
> Last revised: 2026-09-16.

## 1. Goals and Principles

- Application-layer software signature badge, **reversible**: no eFuse / Secure Boot v2.
- Goal: the meta-pass launcher can verify a child firmware's origin; verification passes → detail page boots
  directly; unsigned → BOOT/CANCEL warning page.
- Single trust anchor: **one ECDSA-P256 key pair**. The private key lives only in the macOS Keychain
  (label `com.folotoy.meta-pass.signing`); the public key is compiled into the launcher firmware. Any
  "other private key / stale public key" combination = verification necessarily fails.
- The layout contract defers to the IDF binary format (not "what we believe the format is"); parsers must
  match `esp_image_verify` byte for byte.

## 2. Image and Partition (authoritative facts, IDF v5.5.3)

- Chip ESP32-C3; `esp_image_header_t` is **packed 24 bytes**, `hash_appended` is **byte 23** (bit0).
- `esp_image_segment_header_t` = **[load_addr u32][data_len u32]** (note: load_addr comes first).
- Total image length (`meta.image_len` from `esp_image_verify`):
  `24 + Σ(8 + data_len)` → append 1 checksum byte then **16-byte align** → when `hash_appended=1`,
  **+32** (appended SHA-256).
- Partitions (partitions.csv): ota_0@0x180000/0x1D6000, ota_1@0x360000/0x200000, ota_2@0x560000/0x29E000.

## 3. Slot Layout (single 4 KB metadata sector, since dbbd091)

```
[app image (image_len bytes)] [0xFF pad] [metadata sector (4096B) @ round_up(image_len, 4096)]
```

- Metadata sector offset: `tail_off = (image_len + 4095) & ~4095`; must satisfy `tail_off + 4096 ≤ partition size`.
- App image limit: `partition size − 4096`.
- Three fixed segments inside the sector (positions constant, non-overlapping):
  - `[0..127]`    MSIG signature reserve (variable-length blob ≤ 81 B)
  - `[128..4055]` MAEG easter-egg window (fixed 3928 B)
  - `[4056..4095]` MNAM display-name window (40 B, blob right-aligned)

### 3.1 MSIG blob (ECDSA-P256 signature over the SHA-256 of the first image_len bytes of the image)

```
[4B "MSIG"] [4B payload_len u32 LE (64..72)] [ECDSA-P256 DER signature, payload_len bytes] [1B xor]
xor = byte-wise XOR of the first (8 + payload_len) bytes
```

### 3.2 MAEG (easter egg, not part of the signed digest)

```
Window 128..4055, fixed 3928 B:
[4B "MAEG"] [4B payload_len u32 LE] [text ≤ 3919 B printable ASCII] [0xFF padding] [xor @ last byte of window]
xor covers the first 3927 bytes of the window (padding included)
```

### 3.3 MNAM (display name)

```
Window 4056..4095, right-aligned:
[4B "MNAM"] [1B len (1..32)] [name, printable ASCII] [1B xor (folded over len..len+name)]
The front of the window stays 0xFF
```

## 4. Key Chain

- **Standard fact (trust anchor) = the macOS Keychain private key**, label `com.folotoy.meta-pass.signing`
  (generated by `keychain_keygen.c`; `keychain_sign.c` ECDSA-P256-signs a 32 B digest).
- Derivation chain (Keychain is authoritative; verify level by level — any mismatch is a defect):
  1. Keychain public-key point (`extract-pubkey.c`: `SecKeyCopyExternalRepresentation` → 65 B `0x04+X+Y`);
  2. `public.pem` (SPKI DER, 91 B) — **its trailing 65 B point must == the Keychain point**;
  3. `gen-pubkey.py` rewrites the two embedded DER arrays in `main/meta_sign_pubkey.h` +
     `main/metapass_hook.h` from `public.pem` (must == public.pem DER, 91 B byte-equal; validate.sh compares them).
- Verification commands:
  - Point comparison: `./extract-pubkey` output vs `openssl pkey -pubin -in public.pem -outform DER | tail -c 65`
  - Signature round-trip: `openssl pkeyutl -verify -pubin -inkey public.pem -sigfile <sig.der> -in <digest.bin>`
    (verify the `keychain-sign` output with this; do **not** use `openssl dgst -verify` — it hashes the input again)
- A `private.pem` fallback is forbidden (removed in 8988bab).
- Invariant: **Keychain ↔ public.pem ↔ both embedded DERs stay in four-way sync**; whenever any one changes,
  re-derive from the Keychain.

## 5. Signing Flow (sign-firmware.sh)

1. Parse `image_len`: semantics must match `esp_image_verify` (§2 formula; `hash_appended` reads byte 23 bit0, includes +32).
   - Note: some toolchains insert a **16 B extended header** after the 24 B header — parsers should auto-detect
     (try with extended header first, fall back).
2. `digest = SHA-256(file[0:image_len])` (covering the full image_len, appended hash included).
3. Keychain signing → DER (64..72 B).
4. Assemble the 4096 B sector: MSIG@0 (blob ≤ 81 B), optional MAEG@128, rest 0xFF.
5. Output: `[app as-is][0xFF pad to round_up(image_len,4096)][4096 B sector]`; output name `{name}_{version}-signed.bin`.

> Lesson (observed 2026-09-16): artifacts signed before the toolchain fix (e.g. `pass-radar_signed_v2.bin`) had a
> correct layout/magic/xor, but the digest behind the ECDSA signature did not match the correct semantics
> (full image_len incl. appended hash) → the device necessarily reports `META_SIG_VERIFY_FAIL` → shows "unsigned".
> File-level tests must run against **the exact file being flashed**; stale signed artifacts must be deleted or
> archived after re-signing and never mixed.

## 6. Device-side Verification (boot scan scan_one / parent self-check)

1. `esp_image_verify(ESP_IMAGE_VERIFY)` authoritative check (magic/chip/segment/checksum/appended hash) → `meta.image_len`.
2. Stream `SHA-256(partition[0:image_len])` (4 KB chunks, never whole image in RAM).
3. `tail_off = round_up(image_len, 4096)`; read the sector only if `tail_off + 4096 ≤ part->size`.
4. `meta_sign_verify(digest, image_len, sector, 4096)`:
   magic → payload_len ∈ [64..72] → xor → mbedtls verifies the DER signature with the embedded public key.
5. `signed_fw = (result == META_SIG_OK)`; unsigned → BOOT/CANCEL warning page (defaults to CANCEL).

## 7. Install Channels

### 7.1 USB serial install page (install-slot/)

- **Single-write contract**: the signature sector must land correctly in the same batch as the app. Canonical flow:
  1. `extractAppImage(file)`: parse `imgLen` (same semantics as §5.1) → probe for MSIG at `round_up(imgLen,4096)`
     in the file, extract the full 4096 B tail sector (`tailSector`), record `tailSectorOffset`.
  2. writeFlash #1: `[0:imgLen)` app bytes.
  3. If dispName: merge the MNAM window into the extracted tail sector (**MSIG bytes preserved**).
  4. writeFlash #2: the full 4096 B tail sector @ `slot + tailSectorOffset`.
  - Forbidden: splitting signature/egg/name into multiple writeFlash calls to the same sector (esptool erases the
    whole sector on every write; earlier writes get wiped).
  - Deployment requirement: the page and `_worker.js` must be published in sync with the repo's `install-slot/`;
    caching must not leave browsers on a stale version.

### 7.2 Wi-Fi import (meta_net.c h_upload) — reference implementation of signature protection

- OTA whole-image write (tail sector of signed files included); digest is computed by reading back flash
  (same semantics as scan_one).
- Tail-sector handling: if `meta_sign_detect_sector` finds MSIG → **never write MNAM** (signature protection);
  unsigned + name given → erase the whole sector then write the MNAM window; unsigned + no name → erase to avoid residue.

### 7.3 Slot deletion

- Erase the whole partition (metadata sector included).

## 8. Four-way Consistency Contract (image_len must be byte-identical)

| Party | Carrier | Semantics |
|---|---|---|
| Signing script | sign-firmware.sh (Python) | §2 formula |
| Host verify test | tools/signing/test_integration.c | word-for-word with the script |
| Install page parser | install-slot/extract-app-image.js | §2 formula + 16 B extended-header auto-detect + byte23 `& 1` |
| Device side | esp_image_verify `meta.image_len` | IDF authoritative |

Any directional deviation (wrong hash_appended byte / missing +32 / extended header / checksum pad alignment) causes
**the signature sector to land or the digest to be computed at an offset the device does not read → the device reports
unsigned** — file-level tests cannot cover the device-side implementation; reconcile against IDF source / real binaries
(§2 of this design is that reconciliation result).

## 9. Invariants

1. `tail_off = round_up(image_len, 4096)`, the sector is a full 4096 B, `tail_off+4096 ≤ part_size`.
2. A signed sector must never be overwritten by any MNAM/MAEG write (read-modify-write only, MSIG bytes preserved).
3. The three parsers (script/C/JS) + IDF agree on image_len (§8).
4. Four-way public-key sync (§4).
5. The deployed install page version = the latest commit of the repo's `install-slot/`; stale versions must not stay online.
