## 0. 不可绕过的测试纪律（先读）

**本任务不能仅凭自动化脚本判定完成。真实市场的 28 号固件不能配合当前自动化测试流程。每次涉及该固件的安装成功后，必须暂停并等待用户/现场测试人员人工确认 DATA 的读取与写入是否正常。**

本地 Agent 必须遵守以下硬门禁：

1. 安装操作成功后，立即停止推进后续安装、删除、恢复或清理步骤。
2. 提示人工检查对应玩法的 DATA 存取，并等待明确回复（例如“DATA 读写正常”或明确失败现象）。等待期间不得超时自动放行，不得自行假设通过。
3. **禁止为了完成测试进程、缩短执行时间或让报告变绿而跳过该人工确认任务。** 不得以 HTTP 200、安装接口成功、APP 能启动、日志无错误、mock/模拟数据或自动化断言替代人工 DATA 确认。
4. 未收到人工确认前，该安装场景状态只能记为 `BLOCKED_WAITING_FOR_HUMAN_DATA_CONFIRMATION`，不能记 PASS，也不能继续依赖该场景的后续破坏性操作。
5. 如果当前会话/执行环境不能等待人工输入，停止在该门禁处，保存证据并报告“等待人工确认”；不要继续跑下一阶段。
6. 人工确认必须记录确认人/确认来源、时间、固件与玩法标识、测试了哪些 DATA 操作、结果和备注。未确认、联系不上或反馈含糊，一律不是 PASS。
7. 不要在真实市场 28 号固件上尝试声称自动化已覆盖它；单独标记该固件的人工验收结果。

这项要求优先于任何自动化 runner 的默认流程和“跑完全部测试”的目标。

## 4. 真机测试顺序

### T0：记录基线与确认安全状态

1. 记录设备、固件类型、commit、页面入口和当前 APP/DATA 清单。
2. 确认设备可通信、配对有效、页面版本与预期一致。
3. 在任何删除或恢复覆盖前，确认有可用备份，并确认该设备/固件允许本次测试。
4. 若基线清单、设备身份或固件版本无法确定，停止，不执行破坏性操作。

### T1：安装 APP + DATA（开发/测试固件）

1. 通过目标页面安装带有可识别初始 DATA 的测试玩法。
2. 验证安装 API 的状态、APP 与 DATA 清单、分配范围和最终状态。
3. 如自动化工具可安全读取 DATA，保存初始镜像、偏移、长度和 SHA-256，并执行 byte-for-byte 比对。
4. 验证完成后仍需在设备侧实际打开玩法，执行真实 DATA 读取/写入动作，确认数据确实可用。
5. 记录是否发生重启、错误提示或 DATA 初始化。

### T2：安装成功后的强制人工确认门禁（尤其是市场 28 号固件）

每次安装成功后，必须执行以下流程，不能跳过：

1. 暂停 runner/Agent 的测试流程，不开始下一次安装、删除、备份恢复或数据清理。
2. 向用户/现场测试人员提出明确确认请求，至少询问：
   - 玩法是否能正常启动？
   - 是否能读取安装前已知的 DATA 初始内容/状态？
   - 是否能执行一次可观察的 DATA 写入，并在重新读取（必要时重启玩法后）确认写入值保持正确？
   - 是否出现数据丢失、旧数据串用、初始化异常或读写错误？
3. 等待人工回复。没有回复时保持阻塞状态，不得自动超时通过。
4. 按原始反馈记录结果：
   - 明确确认读写正常：`PASS_HUMAN_CONFIRMED`
   - 发现异常：`FAIL_HUMAN_DATA_IO`，停止后续破坏性测试并保留设备状态与证据
   - 尚未回复/无法判断：`BLOCKED_WAITING_FOR_HUMAN_DATA_CONFIRMATION`
5. 只有明确的人工确认通过后，才允许继续下一个测试场景。

**禁止**用下列内容替代人工确认：安装接口返回成功、APP 能打开、日志没有报错、HTTP 状态码、host test、模拟器、fake device、自动读取 Flash 的单项比对，或“按计划应当正常”的推断。

### T3：备份

1. 在用户明确触发备份后，通过页面导出归档。
2. 检查 ZIP 可解析、manifest 完整，所有条目长度与 SHA-256 一致。
3. 确认归档仅包含所选 APP 组及其 DATA；记录是否含全局 NVS。
4. NVS 归档可能包含 Wi-Fi 凭证及设备配置，归档未加密。不要上传或分享归档，也不要在日志中输出 NVS 原始字节。
5. 将备份存放到受控位置，记录文件大小与 SHA-256，不把备份文件本身提交到 Git。

### T4：恢复到可安全测试的目标设备

1. 先确认目标设备允许写入，且归档来自预期来源。
2. 恢复前记录目标设备的 APP/DATA/NVS 基线。
3. v2 恢复应只恢复 APP + DATA；归档中的全局 NVS 只做完整性校验，不写入目标设备。
4. 记录恢复预检、APP/DATA 写入/回读、carve 提交和最终设备清单。
5. 恢复成功后，必须再次执行 T2 的人工 DATA 读写确认；没有确认不得继续。
6. 若提交结果不确定，停止后续恢复/删除，不要盲目重试或清理 staging。先读取设备状态并收集日志。

### T5：删除与重新安装（仅在备份和人工确认完成后）

1. 删除前确认 APP + 全部关联 DATA 的备份存在且可验证。
2. 通过页面执行 APP 删除；不得尝试单独删除 DATA。
3. 验证 APP 记录与关联 DATA 的处理符合当前设计，其他 APP/DATA 未受影响。
4. 重新安装时验证新分配语义，不得覆盖其他现存 APP。
5. 重新安装成功后再次停在 T2，等待人工确认 DATA 读写。

## 5. 失败处理与停止规则

遇到以下任一情况，立即停止后续破坏性步骤：

- 人工 DATA 确认失败或无法判断。
- 设备固件版本/身份与测试计划不一致。
- 归档校验、DATA 长度/hash、Flash 回读或 carve 状态不一致。
- 恢复 commit/finalize 状态不确定。
- APP 被删除但关联 DATA 的所有权/存储范围无法解释。
- 设备 panic、反复重启、HTTP 认证异常或分区越界行为异常。

保留：
- 当前设备状态与 APP/DATA 清单。
- UART、页面日志、命令输出、HTTP 状态与响应摘要（token 脱敏）。
- 自动化报告、归档 SHA-256、DATA 比对结果。
- 人工确认原文和时间。
- 故障发生时的固件、commit、页面入口及阶段编号。

不要为了继续跑测试而自动清理现场；特别是提交状态不确定时，保留 staging 与现场证据。

## 6. 报告模板

每个场景分别记录，不允许把不同固件/不同页面的结果合并：

| 字段 | 内容 |
|---|---|
| 场景 ID | T0/T1/T2/T3/T4/T5 + 序号 |
| 时间 | 开始/结束时间 |
| 设备/固件 | 开发测试固件或真实市场 28 号固件 |
| 仓库 commit | 完整 SHA |
| 页面入口 | 手机内嵌页 / USB 服务页 |
| 操作 | 安装 / 备份 / 恢复 / 删除 |
| APP/play_id | 实际值 |
| DATA 检查 | 读取内容、写入值、重读结果、重启后结果 |
| 自动化状态 | PASS / FAIL / NOT_RUN |
| 人工确认状态 | PASS_HUMAN_CONFIRMED / FAIL_HUMAN_DATA_IO / BLOCKED_WAITING_FOR_HUMAN_DATA_CONFIRMATION / NOT_REQUIRED |
| 人工反馈 | 原文或准确摘要、确认时间 |
| 证据路径 | report、UART、HTTP 摘要、hash、截图/照片（如有） |
| 失败归因 | 代码 / 固件 / 设备环境 / 操作流程 / 未知 |
| 下一步 | 修复、重测或等待人工 |

## 7. 完成定义

本任务只有同时满足以下条件才算完成：

1. 当前 HEAD 的静态/宿主测试和固件构建通过。
2. 手机内嵌页和 USB 服务页的目标备份/恢复路径均有实际测试记录。
3. 真实市场 28 号固件的每次安装后均有人工 DATA 存取确认；未确认的场景明确保持 BLOCKED。
4. 恢复后的 APP/DATA 能实际读取并写入，且在要求的重读/重启检查后数据正确。
5. 备份归档结构、内容长度和 SHA-256 验证通过；恢复的 DATA 与目标设备状态有证据支持。
6. 所有失败都有日志、归因和处置结论。
7. 没有把自动化成功、页面成功提示或模拟设备结果冒充人工确认或真实市场固件 PASS。

**绝不允许为“完成测试”而跳过 T2 人工确认。测试未完成时，准确报告阻塞原因与下一步，不得伪造通过状态。**
